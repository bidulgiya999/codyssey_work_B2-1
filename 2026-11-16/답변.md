실제 구현과 2026-11-16 VS Code 실행 기록에 근거한 답변입니다. 각 질문의 **답변 멘트 → 코드 위치 → 확인 방법** 순서로 준비했습니다. [실제 작업·출력 기록](./README.md), [터미널 원문](./vscode-terminal-log.txt), [파일 역할·CRUD 안내](./코드_역할과_CRUD.md)를 함께 참고하세요.

## 과제의 핵심을 한 문장으로 설명하기

> Python 표준 라이브러리만 사용해 파일에 영구 저장하는 콘솔 가계부를 만들고, 정상 기능뿐 아니라 잘못된 입력이나 저장 실패에도 데이터를 보호하는 설계까지 설명하는 과제입니다.

구현 조건은 Python 3.10 이상, 세 개 이상의 저장 파일, dataclass 거래 모델, 두 개 이상의 클래스, 세 개 이상의 모듈, 제너레이터 스트리밍, 실제 적용한 데코레이터, 타입 힌트 및 오류 종료 코드입니다. 이 프로그램은 JSONL 세 파일과 계층별 모듈로 충족합니다.

## 실행 명령을 보기 전에

VS Code에서 프로젝트 루트(calculator)를 열고 PowerShell 터미널을 사용합니다. 새 터미널이라면 아래 변수를 먼저 설정합니다.

```powershell
$ledgerPython = 'C:\Users\1234v\AppData\Roaming\uv\python\cpython-3.15-windows-x86_64-none\python.exe'
& $ledgerPython -m budget_app --help
```

이 경로는 현재 컴퓨터 기준입니다. 다른 컴퓨터에서는 설치된 Python 경로를 쓰거나 `python -m budget_app ...`를 실행합니다. 아래 명령은 확인용 예시이며 이미 삭제된 id는 재사용하지 않습니다. 반복 추가·CSV 가져오기는 데이터가 중복될 수 있습니다.

### 1-2. 재실행 후 거래·카테고리·예산이 유지되는가? 저장 파일이 세 개 이상인가?

**답변 멘트:**
> 거래·카테고리·예산을 각각 transactions.jsonl, categories.jsonl, budgets.jsonl에 저장합니다. 각 CLI 명령은 별도의 Python 프로세스이므로, 추가 후 다른 명령으로 조회한 것 자체가 프로세스가 종료되어도 파일에서 다시 읽는 확인입니다.

기본 위치는 프로젝트의 `./data`이며 `--data-dir`로 변경합니다. 파일이 없으면 생성하고 카테고리 파일이 0바이트면 기본 카테고리를 만듭니다. 깨진 JSON을 발견하면 자동 초기화하지 않고 복구를 안내합니다.

**확인 명령:**

```powershell
Get-ChildItem .\data\*.jsonl
& $ledgerPython -m budget_app list --limit 10
& $ledgerPython -m budget_app category list
& $ledgerPython -m budget_app budget show --month 2026-11
```

**코드 위치:** [storage.py](../budget_app/storage.py)의 `DataStore.session()`, `read_jsonl()`, `write_jsonl()`.

### 1-3. category add/list/remove와 사용 중 카테고리 처리가 정상인가?

**답변 멘트:**
> hobby를 추가해 목록에 나타나는 것을 확인하고 사용하지 않는 hobby는 삭제했습니다. 거래가 참조하던 food는 삭제 요청 시 오류와 해결 힌트를 보여주며 보호했습니다. 같은 이름 중복 추가와 마지막 카테고리 삭제도 막습니다.

**코드 위치:** [service.py](../budget_app/service.py)의 `categories()`, `category_add()`, `category_remove()`, `require_category()`.

현재도 가져온 2024년 food 거래가 남아 있으므로 2026년 지출을 삭제했다고 food를 바로 삭제할 수 있는 것은 아닙니다. 카테고리 사용 여부는 전체 거래에서 검사합니다.

### 1-4. budget set이 저장되고 summary에서 사용률·초과 여부를 보여주는가?

**답변 멘트:**
> 월 예산 10,000원을 저장하고 지출 15,000원일 때 사용률 150.0%, 초과액 5,000원 경고를 확인했습니다. 사용률은 해당 월 총지출을 예산으로 나눈 값이며, 월 예산은 별도 파일로 유지됩니다.

**코드 위치:** `BudgetService.set_budget()`, `summary()`와 `cli.execute()`의 summary 분기.

현재는 2026년 지출을 삭제했으므로 다시 요약하면 당시 경고 결과와 달라집니다. 과거 실제 출력은 실습 기록에 보관했습니다. 예산과 지출이 같으면 초과가 아니고, 거래 없는 월은 데이터 없음과 0원 합계를 출력합니다.

### 1-5. import/export가 명시된 UTF-8 CSV 스키마로 동작하는가?

**답변 멘트:**
> CSV는 UTF-8, 헤더 포함이며 date, type, category, amount가 필수이고 memo, tags는 선택입니다. csv 표준 모듈을 써서 한글·쉼표·큰따옴표·개행을 처리합니다. 입력은 UTF-8 BOM도 허용하고 출력은 여섯 열을 고정 순서로 기록합니다.

```csv
date,type,category,amount,memo,tags
2024-01-15,expense,food,15000,점심,"meal,work"
```

헤더 중복·알 수 없는 열·열 개수 불일치를 거부합니다. 등록된 카테고리와 양수 정수 금액이어야 합니다. export에는 `--month` 또는 날짜 범위 조건이 필요합니다. CSV에 id를 싣지 않으므로 import할 때 새 id를 부여합니다.

**코드 위치:** `CSV_FIELDS`, `BudgetService.import_csv()`, `export_csv()`.

**검증 근거:** 실제 export 2건, import 3건을 확인했고 `test_import_and_export_roundtrip_unicode_quotes_and_tags`는 특수문자 CSV 왕복을 검사합니다.

### 1-6. 잘못된 입력·파일 오류에서 스택트레이스 없이 원인과 해결 힌트를 출력하는가?

**답변 멘트:**
> 입력 검증 오류는 AppError에 원인과 hint를 담아 발생시키고, 공통 데코레이터가 두 메시지를 출력합니다. 파일 접근·UTF-8 해석·CSV 오류도 예상 오류로 처리해 스택트레이스 대신 경로와 형식 확인 방법을 안내합니다.

**직접 확인:** 잘못된 날짜, 없는 id, 금액 0, 사용 중인 food 삭제에서 오류와 힌트를 확인했습니다. **자동 테스트:** 깨진 인코딩, 손상된 데이터, 모의 파일 쓰기·교체 실패도 검증합니다. 예상 가능한 오류를 처리하는 것이며 코드상의 모든 프로그래밍 버그를 숨기는 구조는 아닙니다.

**코드 위치:** `models.AppError`, `decorators.command_boundary()`, `cli.Parser.error()`.

PowerShell에 폴더 경로나 출력 예시를 명령으로 입력해서 발생한 오류는 Python 진입 전의 셸 오류입니다. 프로그램의 오류 처리와 구분합니다.

### 1-7. 오류 종료 코드가 0이 아님을 확인할 수 있는가?

**답변 멘트:**
> 금액 0으로 수정 요청한 직후 PowerShell의 LASTEXITCODE가 1임을 확인했습니다. 정상 실행과 전체 테스트는 0, 예상 입력·파일 오류는 1, 명령 문법 오류는 2, EOF나 Ctrl+C 취소는 130으로 구분합니다.

```powershell
& $ledgerPython -m budget_app delete --id NOT-EXISTING-TX
$LASTEXITCODE
```

없는 id 요청이므로 거래를 변경하지 않으며 `1`을 확인할 수 있습니다. `$LASTEXITCODE`는 다음 외부 명령을 실행하기 전에 확인합니다. `__main__.py`의 `SystemExit(main())`이 반환 코드를 프로세스 종료 코드로 전달합니다.

## 항목 2. 모듈·클래스와 안전한 파일 변경

### 2-1. 세 개 이상 모듈의 책임을 어떻게 나눴는가?

**답변 멘트:**
> CLI는 명령·입력·출력, 서비스는 업무 규칙, 저장소는 파일 I/O와 안전한 교체, 모델은 데이터 구조와 검증을 맡습니다. 공통 예외·로그 처리는 decorators로 분리했습니다. 화면 형식 변경이 파일 저장 구현까지 번지지 않도록 나눴습니다.

예: `add` → `cli.execute()` 입력 → `Transaction.create()` 모델 검증 → `BudgetService.add()` 등록 카테고리 검사 → `TransactionRepository.replace()` 병합 → `write_jsonl()` 저장 순서입니다.

`__init__.py`는 패키지 표시, `__main__.py`는 모듈 실행 진입점입니다. 자세한 함수 목록은 [코드 역할 안내](./코드_역할과_CRUD.md)에 있습니다.

### 2-2. 두 개 이상 클래스의 책임 경계를 어떻게 정했는가?

**답변 멘트:**
> 한 거래의 유효성은 Transaction, 거래 파일의 순서와 재작성은 TransactionRepository, 여러 파일을 사용하는 업무 정책은 BudgetService로 나눴습니다. 저장소가 카테고리 정책이나 화면을 알 필요가 없도록 경계를 정했습니다.

| 클래스 | 맡는 책임 | 다른 계층에 맡기는 책임 |
| --- | --- | --- |
| Transaction | 필드·타입·날짜·금액 검증, 저장 dict 변환 | 카테고리 등록 여부·파일 기록 |
| Filters | 조건 표현·검증·거래 일치 판단 | 파일 읽기·화면 출력 |
| DataStore | 경로·세 파일 초기화·잠금·출력 보호 | 수입·지출 집계 |
| TransactionRepository | 정렬된 거래 스트림·id 조회·재작성 | 사용자 입력·카테고리 정책 |
| BudgetService | 거래·예산·카테고리 정책 및 집계·입출력 조합 | 터미널 문구·인자 해석 |
| AppError / Parser | 사용자 오류 정보 / 명령 문법 오류 | 거래 영구 저장 |

### 2-3. 파일 기반 update/delete를 어떻게 안전하게 처리했는가?

**답변 멘트:**
> 대상 id와 입력을 검증한 후 원본 파일을 읽으면서 새 내용을 같은 폴더의 임시 파일에 씁니다. 수정은 옛 거래를 제외하고 바뀐 거래를 정렬 위치에 넣고, 삭제는 대상만 제외합니다. 끝까지 성공하면 flush와 fsync 후 파일을 닫고 os.replace로 교체합니다.

실패 시 임시 파일을 정리하며 원본을 먼저 삭제하지 않습니다. 명령 단위 잠금으로 동시 쓰기의 갱신 유실도 방지합니다. 원자적 교체는 파일 교체의 중간 상태를 보이지 않게 하는 것, 잠금은 두 명령의 충돌을 막는 것이므로 역할이 다릅니다.

**코드 위치:** `BudgetService.update()/delete()` → `TransactionRepository.replace()` → `write_jsonl()` → `atomic_text()`.

**테스트 근거:** `test_atomic_write_failure_does_not_truncate_original`, `test_failed_update_preserves_bytes`, `test_lock_blocks_second_command_and_cleans_up`.

단일 파일 교체 단위의 보장입니다. 모든 하드웨어 장애나 여러 파일의 일괄 트랜잭션까지 보장하지 않으므로 백업이 필요합니다.

## 항목 3. 제너레이터·데코레이터·타입 힌트

### 3-1. list/search 스트리밍을 어떻게 구현했고 왜 유리한가?

**답변 멘트:**
> 파일 객체를 for로 줄 단위 순회하고 read_jsonl에서 yield합니다. iter_all이 거래 모델을 한 건씩 복원하고 search가 조건을 통과한 거래만 다시 yield합니다. CLI는 islice로 limit까지만 요청합니다. 전체 거래 리스트를 만들지 않아 거래 수에 비례하는 메모리가 필요하지 않습니다.

```python
def search(self, filters: Filters) -> Iterator[Transaction]:
    # 카테고리 사전 검증 등은 실제 원본 메서드 참고
    for transaction in self.transactions.iter_all():
        if filters.matches(transaction):
            yield transaction
```

위 예시는 흐름 설명용 발췌입니다. `yield`는 값을 전달한 뒤 다음 요청까지 멈추며 재요청 시 이어갑니다. list는 조건 없는 `Filters()`로 같은 경로를 씁니다. 파일이 날짜 내림차순으로 저장되어 있어 조회 시 전체 정렬이 필요 없습니다. 검색 결과가 드물면 찾기 위해 파일 전체를 읽을 수 있으므로 스트리밍이 항상 검색 시간을 줄이는 것은 아닙니다.

**테스트 근거:** 뒤에 깨진 행을 둬도 `--limit 1`은 읽지 않고 성공하는 `test_limit_does_not_read_entire_transaction_file`.

### 3-2. 데코레이터로 무엇을 분리했고 왜 필요한가?

**답변 멘트:**
> command_boundary로 공통 오류 안내, 종료 코드 처리, 실행 시간 로그를 분리했습니다. execute에 적용해 모든 명령이 같은 공통 처리를 거치게 합니다. 각 업무 함수에서 똑같은 try/except와 시간 측정을 반복하지 않아도 됩니다.

```python
@command_boundary
def execute(args: argparse.Namespace) -> None:
    # 실제 명령 처리
    ...
```

모델·서비스가 잘못된 값을 판단하고 예외를 발생시키면 데코레이터가 원인·힌트를 출력합니다. 정상은 0, 예상 오류는 1, 입력 취소는 130을 반환합니다. `wraps`로 원래 함수 정보를 유지하며, `finally`에서 소요 시간을 기록합니다. `--verbose`를 지정하면 INFO 로그를 볼 수 있습니다. 인자 해석 오류 2는 별도로 `Parser.error()`가 처리합니다.

### 3-3. 타입 힌트의 이점을 실제 코드에서 어떻게 확인했는가?

**답변 멘트:**
> 함수가 어떤 값을 받고 무엇을 반환하는지 코드에 표시했습니다. search의 Iterator[Transaction]은 거래를 한 건씩 반환한다는 계약이고 budgets의 dict[str, int]는 월과 정수 예산의 관계를 보여줍니다. VS Code에서 자동 완성과 타입 확인을 받으며 계층 사이의 오해를 줄일 수 있습니다.

```python
def search(self, filters: Filters) -> Iterator[Transaction]: ...
def budgets(self) -> dict[str, int]: ...
def find(self, identifier: str) -> Transaction: ...
```

`Transaction.amount: int`, `tags: tuple[str, ...]`도 구조를 명확히 합니다. 다만 타입 힌트만으로 실행 중 잘못된 입력이 차단되지는 않습니다. 실제 금액 0과 문자열 형식 검증은 `positive()`와 `__post_init__()`가 담당합니다. 이번 작업은 별도 정적 타입 검사기 통과를 주장하는 것이 아니라 타입 계약과 실제 검증 코드의 역할을 함께 설명합니다.

## 항목 4. 저장 선택·성능·깨진 CSV 처리

### 4-1. JSONL과 CSV의 장단점과 JSONL 선택 이유는 무엇인가?

| 형식 | 장점 | 단점 |
| --- | --- | --- |
| JSONL | 한 줄 한 객체라 순차 처리 가능, 숫자·문자열·태그 배열 표현, 필드 이름이 각 객체에 있음 | CSV보다 파일이 커질 수 있음, 직접 스프레드시트로 보기 불편, 여전히 스키마 검증 필요 |
| CSV | 표 형태가 간단하고 스프레드시트·다른 프로그램과 교환하기 좋음 | 기본적으로 문자열이라 타입 변환 필요, 배열 표현을 별도로 정해야 함, 인용된 쉼표·개행을 파서로 처리해야 함 |

**답변 멘트:**
> 내부 저장은 금액 정수와 태그 배열을 자연스럽게 표현하고 한 줄씩 읽기 좋은 JSONL을 택했습니다. 사용자와의 데이터 교환은 표 형식에 익숙한 CSV로 제공합니다. 두 형식 모두 검증이 필요하고, JSONL이라고 수정·삭제가 자동으로 빨라지는 것은 아닙니다.

### 4-2. 거래 10만 건에서 병목은 어디이며 어떻게 개선할 것인가?

**답변 멘트:**
> 현재 구조는 조회 메모리는 작지만 id 검색과 전체 검색·집계는 선형 탐색이고, 한 건 추가·수정·삭제도 정렬 파일 전체를 다시 쓰는 것이 병목입니다. CSV를 한 행씩 병합해 가져오는 부분은 특히 많은 재작성이 발생합니다.

`n`은 기존 거래 수, `m`은 가져올 행 수, `k`는 지출 카테고리 수입니다.

| 작업 | 현재 비용과 병목 |
| --- | --- |
| list --limit 20 | 파일이 정렬되어 있어 앞 20건만 읽을 수 있음 |
| id 조회 | 인덱스가 없어 최악 O(n) |
| 전체 검색·월별 집계 | O(n) 순회, 요약 순위 정렬은 추가 O(k log k) |
| 한 건 C/U/D | 조회·검증 외에도 O(n) 파일 재작성과 fsync 필요 |
| m건 CSV import | 행마다 스테이징을 다시 써 O(mn + m²) 시간 가능 |
| 명령 동시 실행 | 배타 잠금으로 읽기까지 직렬화되어 대기/실패 가능 |

개선은 다음 순서로 검토합니다. 아래는 제안이며 현재 구현되어 있지는 않습니다.

1. **가져오기 일괄 병합:** 행을 검증해 임시 청크에 모으고 정렬한 뒤, 정렬된 기존 거래와 한 번에 병합합니다. 입력이 메모리보다 크면 외부 병합 정렬을 사용해 메모리를 제한합니다. 청크 파일 열기 수와 정리도 관리합니다.
2. **월별 파일/조회 인덱스:** 월별 조회의 전체 스캔을 줄이고 id 인덱스 도입을 검토합니다. 파일 재작성 시 위치가 바뀌므로 인덱스 갱신·복구 정책까지 함께 설계해야 합니다.
3. **변경 로그와 주기적 정리:** 추가·수정·삭제 이벤트를 기록한 뒤 압축/정리하는 방식도 가능하지만, 읽기에서 최신 상태를 복원하는 비용과 충돌 정책이 늘어납니다.
4. **과제 제약이 풀리면 DB 검토:** Python 표준 sqlite3도 선택할 수 있지만, 이번 과제의 JSONL/CSV 저장 조건을 바꾸는 후속 설계입니다. 현재 제출물을 DB 구현이라고 설명하지 않습니다.

거래 스트림의 버퍼는 O(1)이지만 카테고리·예산 메타데이터와 요약의 카테고리 집계에는 그 개수에 따른 메모리가 필요합니다. 전체 프로그램 메모리가 항상 O(1)이라고 말하지 않습니다.

### 4-3. import CSV에 깨진 행이 섞이면 어떻게 신뢰를 지키는가?

**답변 멘트:**
> 현재는 부분 성공 대신 전체 취소 정책입니다. 원본 거래를 임시 폴더에 복사하고 각 행을 검증·병합한 뒤, 모든 행이 성공해야 원본과 교체합니다. 중간에 한 행이라도 실패하면 스테이징만 폐기해 앞에서 처리한 정상 행도 반영하지 않습니다.

모델 검증 오류는 `CSV N행`과 원인, 전체 취소 힌트를 보여줍니다. 인코딩·CSV 문법·파일 접근 오류는 공통 데코레이터가 안내합니다. 현재는 모든 오류를 모은 별도 CSV 리포트가 아니라 **처음 발견한 오류를 보고 중단**합니다. 인용된 여러 줄 필드가 있으면 `reader.line_num`은 물리 줄 번호 기준입니다.

**증거:** `test_import_invalid_later_row_rolls_back_everything`에서 정상 첫 행 뒤 금액 0의 두 번째 행을 넣어 원본 바이트가 그대로이고 임시 폴더도 정리되는지 확인합니다. 실제 시연에서는 정상 CSV 3건을 가져왔고, 깨진 CSV 시나리오는 자동 테스트에서 검증했습니다.

향후 모든 오류를 보고하려면 먼저 임시 공간에서 전체를 검증해 줄 번호별 오류 목록을 반환하고, 오류가 없을 때만 반영할 수 있습니다. 부분 성공을 추가한다면 사용자가 정책을 명시적으로 고르게 하고 성공·실패 행 수 및 재시도 중복 처리까지 설계해야 합니다.
