## 1. VS Code 실행 준비

이 컴퓨터의 작업 폴더는 `C:\Users\1234v\Desktop\calculator`입니다. VS Code의 **파일 → 폴더 열기**로 해당 폴더를 열고 **터미널 → 새 터미널 → PowerShell**을 선택합니다.

```powershell
cd "C:\Users\1234v\Desktop\calculator"
$ledgerPython = 'C:\Users\1234v\AppData\Roaming\uv\python\cpython-3.15-windows-x86_64-none\python.exe'
& $ledgerPython -m budget_app --help
```

- `$ledgerPython`은 이 컴퓨터에 설치된 Python의 실행 경로입니다. 새 터미널을 열면 다시 설정합니다.
- 다른 컴퓨터는 설치된 Python 경로로 바꾸거나 `python -m budget_app ...`로 실행합니다.
- `PS C:\...>`는 터미널이 자동 표시하는 현재 위치입니다. 직접 입력하지 않습니다.
- 폴더로 이동할 때는 경로만 입력하지 않고 `cd "경로"`를 사용합니다.
- 명령 끝에 `\`를 붙이지 않습니다. 명령을 한 줄씩 실행합니다.
- 명령은 `PS C:\...>`에서 입력하고, `날짜:` 등 질문이 나오면 답만 입력합니다.

**확인 결과:** 도움말에 `add`, `list`, `search`, `summary`, `budget`, `category`, `update` 등의 명령이 표시되었습니다.

**설명 멘트:**

## 6. 예산 설정과 월별 요약

### 명령

```powershell
& $ledgerPython -m budget_app budget set --month 2026-11 --amount 10000
& $ledgerPython -m budget_app summary --month 2026-11 --top 3
```

### 기능과 확인 결과

11월 예산을 10,000원으로 저장하고 요약을 실행했습니다. 월급과 점심 거래를 각각 한 건씩 저장한 시점의 결과는 다음과 같습니다.

| 항목 | 결과 |
| --- | ---: |
| 총수입 | 3,000,000원 |
| 총지출 | 15,000원 |
| 잔액 | 2,985,000원 |
| 월 예산 | 10,000원 |
| 사용률 | 150.0% |
| 초과액 | 5,000원 |

예산 초과 경고가 정상적으로 출력되는 것을 확인했습니다. `--top 3`은 지출 합계가 큰 카테고리를 최대 3개 표시합니다.

**설명 멘트:**
> 월별 수입, 지출과 잔액을 계산하고 카테고리별 지출 순위를 보여줍니다. 월 예산이 있으면 지출 기준 사용률을 표시하고 예산을 넘으면 경고합니다.

### 실제 VS Code 실행 출력

## 평가 핵심 개념과 설명 멘트

설명 순서: “무엇인지 → 우리 코드에서 어떻게 쓰는지 → 왜 쓰는지”

### 1. 모듈 분리: 역할별로 파일 나누기

쉽게 이해하기:
가게에서 주문을 받는 사람과 요리하는 사람의 역할을 나누듯, 프로그램도 역할별로 파일을 나눈 것입니다.

우리 코드의 역할:
- cli.py: 사용자 명령과 입력을 받고 결과를 출력합니다.
- models.py: Transaction dataclass와 날짜·금액 등 입력 검증을 정의합니다.
- service.py: 거래 관리, 검색, 요약, 예산과 카테고리의 업무 규칙을 처리합니다.
- storage.py: 파일 읽기, 잠금과 안전한 저장을 담당합니다.
- decorators.py: 공통 오류 처리와 실행 시간 측정을 담당합니다.

**평가 멘트:**
> “입출력, 업무 규칙, 파일 저장과 데이터 모델을 역할별로 분리했습니다. 기능을 수정할 때 관련 부분을 쉽게 찾을 수 있고 유지보수하기 좋습니다.”

추가 질문에 답하기:
화면 문구는 주로 cli.py, 저장 방식은 storage.py에서 확인합니다. 거래 추가는 CLI 입력 → 모델 생성·검증 → 서비스의 카테고리 확인 → 저장소 기록 순서로 진행됩니다.

### 2. 제너레이터: 필요한 데이터를 한 건씩 전달하기

쉽게 이해하기:
책 전체를 복사해 놓고 읽는 대신 한 페이지씩 읽는 방식입니다.

우리 코드에서 사용하는 방법:
storage.py의 read_jsonl()이 파일을 줄 단위로 읽고 yield로 한 건씩 전달합니다.
TransactionRepository.iter_all()이 거래 모델로 변환하고, service.py의 search()가 조건에 맞는 거래를 다시 yield합니다.
cli.py는 islice로 목록의 최대 출력 건수를 제한합니다.

**평가 멘트:**
> “거래 파일 전체를 메모리에 올리지 않고 제너레이터로 한 건씩 읽습니다. 목록에서 limit을 지정하면 필요한 건수까지만 처리할 수 있어 메모리 사용을 줄입니다.”

추가 질문에 답하기:
yield는 값을 하나 전달한 뒤 잠시 멈추고, 다음 값을 요청받으면 이어서 실행합니다.
제너레이터 자체가 최신순 정렬을 해주는 것은 아닙니다. 저장할 때부터 거래를 날짜 내림차순으로 유지해 조회 시 전체 정렬을 피합니다.
검색이나 요약처럼 필요한 조건에 따라 파일 끝까지 읽을 수 있지만, 거래 전체를 한꺼번에 메모리에 쌓지는 않습니다.

### 3. 데코레이터: 공통 처리를 함수에 붙이기

쉽게 이해하기:
각 기능에 오류 처리와 시간 측정을 반복해서 적는 대신 공통 처리로 감싸는 방법입니다.

우리 코드에서 사용하는 방법:
decorators.py에서 command_boundary를 정의하고, cli.py의 execute 함수 위에 @command_boundary를 붙였습니다.
명령 실행을 감싸서 오류 메시지와 힌트 출력, 종료 코드 처리, 실행 시간 로그를 담당합니다.
실행 시간 로그는 --verbose 옵션을 지정했을 때 표시합니다.

**평가 멘트:**
> “여러 명령에 공통으로 필요한 오류 처리와 실행 시간 측정을 데코레이터로 분리했습니다. 각 기능에서는 업무 로직에 집중하고 공통 처리를 반복해서 작성하지 않도록 했습니다.”

추가 질문에 답하기:
금액 0이 잘못된 값이라는 판단은 모델의 검증 함수가 합니다.
데코레이터는 그 오류를 받아 안내 메시지와 힌트를 출력하고 종료 코드 1로 처리합니다.
즉, 입력 검증 자체와 공통 오류 처리는 역할이 다릅니다.

### 4. 원자적 파일 교체: 새 파일을 완성한 후 바꾸기

쉽게 이해하기:
원본 문서를 바로 지우면서 고치는 대신 수정본을 먼저 완성하고 원본과 교체하는 방식입니다.

우리 코드에서 사용하는 방법:
storage.py의 atomic_text()에서 다음 순서로 처리합니다.
1) 원본과 같은 폴더에 임시 파일을 만듭니다.
2) 변경된 내용을 임시 파일에 끝까지 기록합니다.
3) flush()로 Python의 출력 버퍼를 비우고 fsync()로 파일 기록을 운영체제에 요청합니다.
4) 파일을 닫은 뒤 os.replace()로 원본 파일을 교체합니다.

**평가 멘트:**
> “수정이나 삭제할 때 원본 파일을 바로 덮어쓰지 않습니다. 임시 파일에 내용을 모두 기록한 뒤 원자적으로 교체합니다. 교체 전에 오류가 발생하면 기존 파일을 유지해 데이터 손상을 줄입니다.”

추가 질문에 답하기:
원자적 교체는 교체 중간 상태 대신 교체 전 파일 또는 교체 후 파일을 보도록 하는 것입니다.
동시 실행으로 인한 덮어쓰기는 별도의 잠금 파일로 방지합니다. 원자적 교체만으로 동시 쓰기 문제까지 해결되는 것은 아닙니다.
이 보장은 단일 파일 교체 단위입니다. 모든 저장장치 장애까지 막는 것은 아니므로 ZIP 백업 기능도 제공합니다.

### 5. 네 가지를 연결한 최종 설명

> “역할별로 모듈을 나누고, 조회는 제너레이터로 한 건씩 처리했습니다. 공통 오류 처리는 데코레이터로 분리했으며, 저장은 임시 파일을 완성한 뒤 원자적으로 교체해 기존 데이터를 보호했습니다.”

구현과 테스트 실행은 이미 완료한 상태이며, 이 자료는 평가 때 구조와 설계 이유를 설명하기 위한 참고용입니다.

## 평가 준비 상태

과제 프로그램 구현, 단계별 기능 시연, 오류 처리 확인, 백업 생성, 전체 자동 테스트 및 이번 작업 기록 작성을 완료했습니다. 기존 루트 README에는 실행 방법, 세 저장 파일의 위치와 형식, 명령 예시와 CSV 스키마가 정리되어 있습니다.

평가 때는 VS Code에서 프로젝트 루트를 열고 이 문서의 순서로 시연하면 됩니다. 이미 등록된 데이터를 기준으로 다시 실행하면 합계와 거래 id가 달라질 수 있습니다. 같은 CSV를 다시 가져오면 중복 거래가 생성되므로 유의합니다. 새 터미널에서는 `$ledgerPython` 변수를 다시 설정하고, 수정·삭제 대상은 그때의 목록에서 확인합니다.

구조 설명은 다음 네 가지를 준비합니다.

- CLI / 서비스 / 저장소 / 모델을 나눈 이유와 각 책임
- `yield` 제너레이터로 파일을 한 건씩 읽는 방식
- 공통 오류 처리와 시간 로그에 데코레이터를 적용한 이유
- 타입 힌트 및 임시 파일 기록 후 원자적 교체로 얻는 효과

이 문서는 실행과 확인 결과를 기록한 자료이며 평가자의 최종 점수나 별도 제출 절차의 완료를 의미하지는 않습니다.

## 현재 시점의 정리

- 실행 확인 범위: 도움말 → 수입 추가 → 목록 → 검색 → 지출 추가 → 예산/요약 → 수정 → 잘못된 입력과 종료 코드 → 카테고리 관리와 삭제 보호 → CSV 내보내기 → CSV 가져오기 → 거래 삭제와 재삭제 오류 처리 → 백업 생성과 ZIP 구성 확인 → 전체 자동 테스트 30개 통과.
- 2026년 11월의 12,000원 지출을 삭제했습니다. 추가 입력이 없다면 해당 월은 수입 3,000,000원, 지출 0원, 잔액 3,000,000원이며 예산 사용률은 0%입니다. 이는 현재 거래에 따른 예상 요약으로, 삭제 후 summary를 별도로 실행한 결과는 아닙니다. CSV 예제는 2024년 1월 거래이므로 2026년 11월 요약에 합산되지 않습니다. 첨부 로그의 삭제 후 목록에서 월급 1건과 가져온 3건, 총 4건을 직접 확인했습니다.
- 저장 파일은 프로젝트 루트의 `data/transactions.jsonl`, `data/categories.jsonl`, `data/budgets.jsonl`입니다.
- 이 날짜 폴더는 실행 방법과 실습 결과를 기록합니다. 프로그램 소스와 실제 실행 데이터는 별도이며, 이 문서를 실행하거나 업로드하는 것만으로 거래가 추가되지는 않습니다.
- 백업 생성과 ZIP 안의 세 파일 구성을 확인했으며, 전체 자동 테스트 30개 통과와 OK, 종료 코드 0으로 마지막 실행 검증을 완료했습니다.
